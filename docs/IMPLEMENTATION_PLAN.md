# SweetNet: путь к первому релизу

Статус: исходное задание v1 реализовано в коде; фактические результаты и оставшиеся проверки см. в `docs/PROGRESS.md`.

## 1. Результат

Создать небольшую закрытую социальную сеть: владелец приглашает друзей, участники входят в свои аккаунты и публикуют текст и фотографии в общей ленте. Интерфейс на русском, удобен с телефона и компьютера.

Первый релиз включает все четыре части:

| Часть | Технология | Назначение |
| --- | --- | --- |
| p1 — DataBase | PostgreSQL | Пользователи, приглашения, сессии, посты, метаданные фотографий |
| p2 — Backend | Go, стандартный `net/http`, роутер chi, драйвер pgx | Правила приложения, права доступа, работа с базой и файлами |
| p3 — API | REST, JSON, префикс `/api/v1`, спецификация OpenAPI 3.1 | Договор между браузером и Go-сервером: адреса запросов, данные и ошибки |
| p4 — Web-App | React, TypeScript, Vite, React Router, обычный CSS | Страницы входа, лента, публикация, профиль, управление участниками |

API — часть Go-backend, отдельный сервис для него не нужен. React обращается к нему через `fetch`. Vite нужен для разработки и сборки; готовые frontend-файлы раздаёт Go. Отдельный Node.js-сервер в production не требуется.

Используй актуальные стабильные совместимые версии на момент реализации. Проверь требования к Go и Node.js в официальной документации, зафиксируй версии в Dockerfile, go.mod и package-lock.json. Не используй плавающий тег `latest` в итоговой конфигурации.

## 2. Принятые продуктовые решения

- Начальная аудитория — один круг примерно из 5–50 человек; это ориентир масштаба, не заявленная протестированная ёмкость.
- Все активные участники видят все публикации, в том числе созданные до их вступления. Это явно написано на странице регистрации.
- Публичной регистрации, публичных постов, подписок, заявок в друзья и нескольких групп в v1 нет.
- Владелец создаёт одноразовые приглашения, отзывает их и отключает аккаунты участников. Обычные участники приглашать не могут.
- Отключённый участник сразу теряет доступ, включая уже открытые сессии. Его посты сохраняются; владелец может удалить их.
- Приватность означает контроль доступа к сервису. Сквозное шифрование в v1 не входит; участники могут сохранить увиденное, администратор сервера имеет технический доступ к данным.

Это рабочие допущения, позволяющие начать без дополнительных вопросов. Если владелец позже изменит модель доступа, сначала обнови соответствующие правила и тесты.

## 3. Функции первого релиза

### Аккаунты и приглашения

- Первый владелец создаётся локальной CLI-командой. Пароль вводится скрыто через stdin/TTY, не аргументом команды. Команда работает только если владельца ещё нет; повторный запуск не создаёт второго владельца. Гонка параллельных запусков тоже исключена.
- Приглашение действует 7 суток, используется один раз. Секрет генерируется криптографически стойко, хранится в БД только как хеш. Ссылка показывается владельцу при создании; отправляет её друзьям сам владелец.
- Регистрация: приглашение, уникальный username, отображаемое имя, пароль. Username — 3–32 ASCII-символа `[a-z0-9_]`, нормализуется в нижний регистр; display name — 1–80 символов. Пароль — 12–128 символов, без скрытого обрезания или нормализации.
- Неверное, просроченное, отозванное или использованное приглашение не позволяет зарегистрироваться. Проверка и расходование приглашения вместе с созданием пользователя выполняются транзакционно.
- Вход по username и паролю, выход, получение текущего пользователя, смена собственного пароля с проверкой текущего.
- Профиль позволяет изменить отображаемое имя. Username в v1 не меняется. Email, аватары и самостоятельное восстановление по почте отложены.
- Для забытого пароля предусмотрена локальная CLI-команда администратора с безопасным вводом нового пароля и отзывом сессий. Она не выводит пароль в лог.

### Публикации

- Пост содержит текст до 5000 символов и до 4 фотографий. Допустим текст без фото или фото без текста; полностью пустой пост запрещён.
- Форматы загрузки: JPEG и PNG, до 10 MiB на исходный файл. Проверяются реальный формат, размер и количество пикселей (до 25 мегапикселей), а не только расширение. Общий лимит multipart-запроса — 42 MiB.
- Сервер декодирует и заново кодирует изображения, удаляя метаданные, включая EXIF/GPS. SVG, GIF, видео и произвольные вложения не принимаются.
- Лента идёт от новых постов к старым, по 20 записей; максимальный размер страницы 50. Курсор основан на `(created_at, id)` и не даёт дубликатов при одинаковом времени создания.
- Карточка показывает автора, дату, текст и фотографии. Есть отдельная страница поста.
- Автор может редактировать текст и удалять свой пост. Замена фотографий после публикации отложена. Редактирование не может сделать пост пустым.
- Владелец может удалить любой пост, но не редактировать чужой текст.
- Лайки, комментарии, личные сообщения, поиск, уведомления, видео и мобильные приложения — после v1.

### Интерфейс

- Страницы: вход, регистрация по приглашению, лента, новый пост, просмотр поста, свой профиль, управление приглашениями и участниками для владельца.
- Понятные состояния загрузки, пустой ленты, ошибки и истёкшей сессии; подтверждение удаления; защита от повторного отправления формы во время запроса.
- Предпросмотр выбранных фотографий и удаление из формы до отправки. Лимиты видны пользователю.
- Адаптивная вёрстка от 360 px, читаемый текст, подписи полей, управление с клавиатуры, видимый фокус. При неудачной отправке текст поста не теряется.
- На регистрации ясно сказано: «Публикации доступны всем участникам этого закрытого круга».
- Проверки frontend помогают пользователю, но backend независимо проверяет все ограничения.

## 4. Архитектура и хранение

```text
Браузер: React
    │ HTTPS, тот же origin
    ▼
Go: frontend-файлы + /api/v1 + защищённая выдача фото
    ├── PostgreSQL: учётные записи, права, контент, сессии
    └── закрытый каталог uploads: обработанные изображения
```

Один Go-процесс, один PostgreSQL, постоянные volumes для БД и файлов. Модульный монолит с понятными пакетами; не вводи абстракции без задачи. SQL-запросы через pgx, версионированные SQL-миграции через goose. Для v1 ORM не нужен.

В локальной разработке Vite проксирует `/api` к Go. В production Go раздаёт собранную SPA; её fallback не должен перехватывать неизвестные `/api/*`. Для будущего VPS подготовь пример Caddy перед Go для HTTPS. Production работает на одном origin, открытый CORS не нужен.

Пример структуры, которую можно уточнять без изменения архитектуры:

### Таблицы PostgreSQL

| Таблица | Основные поля и ограничения |
| --- | --- |
| `users` | UUID `id`, уникальный нормализованный `username`, `display_name`, `password_hash`, `role` (`owner`/`member`), `is_active`, `created_at`, `updated_at`; не более одного owner |
| `invites` | UUID `id`, уникальный `token_hash`, `created_by`, `expires_at`, `used_by`, `used_at`, `revoked_at`, `created_at` |
| `sessions` | UUID `id`, `user_id`, уникальный `token_hash`, `expires_at`, `created_at` |
| `posts` | UUID `id`, `author_id`, `body`, `created_at`, `updated_at`; индекс `(created_at DESC, id DESC)` |
| `post_images` | UUID `id`, `post_id`, уникальный `storage_key`, `mime_type`, `byte_size`, `width`, `height`, `position`, `created_at`; уникальная позиция внутри поста |

У внешних ключей явно задай поведение удаления. Используй `timestamptz` и UTC, отображай время локально в браузере. Никогда не возвращай хеши паролей и секретов в API. Ограничения ролей, внешние ключи и уникальность обеспечиваются БД; межтабличное правило «текст или фото» проверяется сервисом в транзакции.

### Фотографии

Создание поста принимает текст и фотографии одним multipart-запросом. Сначала проверь и обработай весь набор во временном закрытом каталоге, затем запиши файлы под случайными серверными именами и сохрани пост с метаданными в транзакции. При ошибке очисти новые файлы. При аварийном завершении возможные сироты убирает отдельная безопасная команда сверки, работающая при остановленном приложении и с dry-run по умолчанию.

Каталог uploads не является публичной статикой. Фото выдаются только по `/api/v1/media/{id}` после проверки активной сессии и существования связанного поста. Имя файла от клиента никогда не используется как путь на диске. При удалении поста доступ к изображениям прекращается сразу после удаления записей; ошибки физической очистки фиксируются для повторной уборки.

## 5. Авторизация и приватность

- Используй серверные сессии, не JWT. Cookie содержит случайный секрет не менее 32 байт, в БД хранится его SHA-256-хеш. Срок сессии — 30 дней без автоматического продления в v1.
- Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`; `Secure` обязателен при HTTPS. Локальный HTTP разрешается только в явно включённом development-режиме.
- Пароли хешируй Argon2id через поддерживаемую библиотеку со случайной солью; выбери и документируй параметры по актуальной рекомендации OWASP и замерам на целевом окружении. Самостоятельную криптографию не пиши.
- Для всех изменяющих HTTP-запросов проверяй точное совпадение `Origin` с настроенным `APP_ORIGIN`; отсутствующий или чужой Origin отклоняй. Это распространяется также на вход, регистрацию и multipart-загрузку. CLI работает отдельно от публичного HTTP API. GET не изменяет состояние.
- В каждом защищённом запросе проверяй срок сессии и `is_active` пользователя. Выход удаляет текущую сессию; смена/сброс пароля и отключение аккаунта отзывают все сессии. После смены пароля нужен повторный вход.
- Обычный участник не может получить роль owner из регистрационного JSON или изменить её через профиль. Нельзя отключить единственного владельца через API.
- Ограничь частоту входа и регистрации по IP и нормализованному username, создания приглашений и загрузок по пользователю. В v1 допустим ограниченный по памяти limiter внутри одного процесса. Не доверяй произвольному `X-Forwarded-For`; прокси должен быть явно доверенным.
- Для приватных JSON-ответов и изображений выставляй `Cache-Control: no-store`, для изображений также `X-Content-Type-Options: nosniff`. Не кэшируй приватный контент в service worker или localStorage; очищай состояние frontend при выходе.
- Текст поста выводится как текст, без исполнения HTML. Добавь CSP, согласованную с frontend, и запрет встраивания в чужие страницы.
- Не логируй тела форм входа/регистрации, Cookie, приглашения и содержимое постов. Ссылку приглашения сделай с токеном во fragment (`/join#token=...`), frontend передаёт его в теле POST; установи `Referrer-Policy: no-referrer`.
- Для входа используй общую ошибку без раскрытия существования username. Неавторизованный запрос к приватным данным получает 401; недостаток прав — 403; отсутствующий ресурс — 404.
- PostgreSQL не публикуется наружу. Readiness проверяет БД, но не раскрывает детали соединения.

## 6. Контракт REST API

Сначала создай `api/openapi.yaml` и поддерживай его вместе с обработчиками и frontend. Опиши JSON/multipart-схемы, cookie-аутентификацию, требования Origin, ограничения, пагинацию и все используемые коды ошибок. Спецификация доступна в репозитории; публичный Swagger UI не требуется.

| Метод и путь | Доступ | Назначение |
| --- | --- | --- |
| `GET /healthz` | Публично | Проверка процесса без внутренних деталей |
| `GET /readyz` | Публично | 200 если БД готова, иначе 503 |
| `POST /api/v1/auth/register` | Приглашение | Создать member и сессию |
| `POST /api/v1/auth/login` | Публично | Создать сессию |
| `POST /api/v1/auth/logout` | Участник | Удалить сессию и cookie |
| `GET /api/v1/me` | Участник | Текущий профиль |
| `PATCH /api/v1/me` | Участник | Изменить display name |
| `POST /api/v1/me/password` | Участник | Сменить пароль и отозвать сессии |
| `GET /api/v1/posts?cursor=...&limit=20` | Участник | Лента, `items` и `next_cursor` |
| `POST /api/v1/posts` | Участник | Пост: multipart `body` и повторяющиеся `images` |
| `GET /api/v1/posts/{id}` | Участник | Пост и метаданные фото |
| `PATCH /api/v1/posts/{id}` | Автор | Изменить текст |
| `DELETE /api/v1/posts/{id}` | Автор или owner | Удалить пост |
| `GET /api/v1/media/{id}` | Участник | Защищённое изображение |
| `GET /api/v1/admin/invites` | Owner | Список и статусы, без секретов |
| `POST /api/v1/admin/invites` | Owner | Создать приглашение, один раз вернуть ссылку |
| `DELETE /api/v1/admin/invites/{id}` | Owner | Отозвать неиспользованное приглашение |
| `GET /api/v1/admin/users` | Owner | Участники и статусы |
| `PATCH /api/v1/admin/users/{id}` | Owner | Изменить только `is_active` для member |

Единая ошибка: `{"error":{"code":"VALIDATION_ERROR","message":"Понятное сообщение","fields":{"body":"Слишком длинный текст"}}}`. `fields` опционально. Используй 201 для создания, 204 для успешного удаления без тела, 400 для некорректного ввода, 409 для конфликта, 413 для превышения размера, 415 для неподдерживаемого файла, 429 для rate limit. В 500 не возвращай SQL, пути и stack trace.

## 7. Путь разработки и контрольные точки

Порядок зависимостей: каркас → p1 → p2/p3 → p4 → совместная проверка релиза. Backend и API разрабатываются вместе. Этапы ниже — исполняемый backlog, а не предложение остановиться после планирования.

### Этап 0. Каркас и воспроизводимый запуск

- Проверить окружение, создать backend и frontend, зафиксировать зависимости, `.gitignore`, `.env.example`, Makefile и Docker Compose.
- Создать минимальную OpenAPI-спецификацию и health/readiness; настроить конфигурацию, graceful shutdown, HTTP timeouts, лимиты запросов и безопасные логи.
- Подготовить multi-stage Dockerfile: frontend build, Go build, непривилегированный runtime. Runtime получает только необходимые файлы.
- Контроль: backend и frontend собираются, PostgreSQL поднимается с healthcheck. Readiness показывает недоступность БД при её остановке.

### Этап 1. p1 — PostgreSQL

- Реализовать миграции таблиц, ограничений и индексов из раздела 4, подключение через pgxpool.
- Добавить команды применения миграций и отдельную тестовую БД. Откат разрушающих миграций не запускать автоматически на пользовательской базе.
- Контроль: чистая БД мигрирует, повторный запуск миграций безопасен; ограничения уникальности, FK и ролей проверены на PostgreSQL.

### Этап 2. p2 + p3 — закрытый доступ

- Реализовать CLI создания владельца, приглашения, регистрацию, вход, выход, профиль и пароли.
- Реализовать middleware сессии, активного пользователя, owner, Origin и rate limit; управление участниками.
- Дополнить OpenAPI реальными запросами и ошибками.
- Контроль: приглашение принимается ровно один раз даже при двух параллельных регистрациях; отключение участника и смена пароля отзывают сессии; member не выполняет admin-запросы.

### Этап 3. p2 + p3 — публикации и фотографии

- Реализовать CRUD постов, курсорную ленту, проверку владельца поста, обработку и защищённую выдачу изображений.
- Реализовать очистку после ошибок загрузки и удалений, безопасную сверку файлов и метаданных.
- Контроль: работают посты с текстом и/или фото, ограничения загрузки, одинаковые даты в пагинации, запрет изменения чужого поста, запрет прямого доступа к фото без активной сессии.

### Этап 4. p4 — Web-App

- Реализовать страницы из раздела 3, клиент API и работу с cookie/401.
- Подключить формы к реальному Go API и PostgreSQL. Моки допустимы только внутри тестов.
- Добавить UX загрузок, ошибок, пустого состояния, мобильной вёрстки и выхода.
- Контроль: из браузера можно создать приглашение, зарегистрировать друга, опубликовать пост с фотографией и увидеть его во втором аккаунте.

### Этап 5. Проверка полного релиза

- Go: форматирование, `go vet ./...`, `go test ./...`, race detector при поддержке окружения; integration-тесты на отдельной PostgreSQL.
- Frontend: TypeScript typecheck, lint, production build. Проверить OpenAPI валидатором и тестами фактических HTTP-запросов.
- Playwright: сценарии двух независимых browser contexts плюс гость. Проверить мобильную ширину 360 px и desktop.
- Добавить CI для backend, frontend и ключевых интеграционных/браузерных тестов с PostgreSQL. Секреты и реальные данные в CI не использовать.
- Контроль: все критерии раздела 8 проверены; команды и фактические результаты записаны в `docs/PROGRESS.md`. Непроведённые проверки отмечены явно.

### Этап 6. Запуск и эксплуатация

- Сделать путь локального запуска из чистого checkout: копирование `.env.example`, безопасная настройка dev-переменных, `docker compose up --build`, документированная CLI-команда создания владельца. Миграции должны выполняться до запуска приложения через отдельный одноразовый сервис или эквивалентный проверенный механизм.
- Подготовить `docs/DEPLOYMENT.md`: один VPS, домен, Caddy/HTTPS, env, закрытая БД, постоянные volumes, обновление и откат версии приложения. Не откатывать схему с потерей данных автоматически.
- Добавить backup/restore БД и uploads. Для согласованной копии в v1 допустима короткая остановка приложения на запись при работающей БД; скрипт должен восстановить запуск и при ошибке. Резервные копии содержат приватные данные, не включать их в git; описать защищённое хранение вне сервера.
- Проверить восстановление в отдельное чистое окружение: аккаунты, посты и фотографии доступны, правила доступа сохранены.
- Контроль: README позволяет начинающему запустить и остановить сервис, пригласить друга, сделать и восстановить backup. Production-конфигурация подготовлена, но её работоспособность на реальном домене нельзя заявлять без фактической проверки.

## 8. Критерии готовности v1

Отмечай в `docs/PROGRESS.md` только после проверки:

- [ ] Новый checkout запускается по инструкции; данные переживают перезапуск контейнеров.
- [ ] Владелец создаётся без публичного bootstrap-endpoint и стандартного пароля.
- [ ] Друг регистрируется по приглашению; повторное, просроченное и отозванное приглашение отклоняются.
- [ ] Участник A публикует текст и фото; участник B видит их в ленте и на странице поста.
- [ ] Гость не получает ленту, профиль, пост или изображение даже по известному ID/прямому URL.
- [ ] B не может редактировать или удалять пост A; owner может удалить его, но не переписать текст.
- [ ] Неактивный участник сразу лишается доступа; повторное включение не оживляет старые сессии.
- [ ] Logout, смена и сброс пароля отзывают соответствующие сессии; просроченная сессия отклоняется.
- [ ] Чужой или отсутствующий Origin блокирует изменяющие запросы; rate limit проверен.
- [ ] Фальшивый MIME, слишком большой файл, лишние фотографии и изображение с чрезмерным числом пикселей отклоняются; EXIF удаляется.
- [ ] Пустой пост запрещён; авторизация нельзя обойти подменой author_id, role или полей JSON.
- [ ] После удаления поста фото недоступны; приватные ответы не кэшируются; после выхода лента очищена.
- [ ] Лента корректно листается; ошибки загрузки и истёкшая сессия понятны пользователю.
- [ ] Проверены интерфейс на 360 px, навигация с клавиатуры и основные desktop-сценарии.
- [ ] Есть согласованная OpenAPI-спецификация, миграции, воспроизводимые проверки и журнал результатов.
- [ ] Backup восстановлен в отдельное окружение с рабочими постами и фотографиями.
- [ ] В репозитории и логах нет реальных секретов, приглашений и пользовательских данных.

## 9. После первого релиза

Сначала собрать обратную связь от друзей. Возможный порядок: комментарии и лайки → аватары и восстановление доступа → уведомления → несколько закрытых кругов и отдельные права → видео и внешнее файловое хранилище при реальной необходимости. Эти функции не являются условием завершения v1.
