# SweetNet — инструкции для Codex

SweetNet — закрытая социальная сеть для владельца и его друзей. Общайся с владельцем на русском языке, код и имена сущностей пиши на английском.

## Основное задание

Полное задание, архитектура, этапы и критерии готовности первого релиза находятся в `docs/IMPLEMENTATION_PLAN.md`. Прочитай его перед реализацией. Если пользователь просит начать или продолжить создание SweetNet, выполняй этот план, а не ограничивайся предложением плана.

## Порядок работы

1. Проверь существующие файлы, git status и инструкции. Сохрани чужие изменения. Не пересоздавай уже работающий проект.
2. Прочитай `docs/IMPLEMENTATION_PLAN.md` и `docs/PROGRESS.md`, если второй файл существует. Сопоставь отметки с реальным кодом.
3. При начале реализации создай `docs/PROGRESS.md`: этап, статус, результат проверки, оставшиеся задачи и следующий шаг. Изначально все этапы не выполнены.
4. Реализуй этапы последовательно. После успешной проверки переходи к следующему без запроса разрешения на каждый этап. Рутинные технические решения принимай самостоятельно в рамках задания.
5. Если для отдельного шага не хватает инструмента, доступа или секрета, точно опиши препятствие и продолжай независимую работу. Не заявляй, что непроведённая проверка пройдена.
6. Обновляй прогресс после каждого этапа и перед завершением сессии. При продолжении начинай с первого незавершённого этапа.
7. Заверши реализацию проверкой критериев релиза и инструкцией для начинающего: как запустить, создать владельца, пригласить друзей и сделать резервную копию.

## Ограничения

- Стек: PostgreSQL, Go, REST/JSON с OpenAPI, React + TypeScript + Vite. Архитектура — один backend и один web frontend в одном репозитории.
- Один закрытый круг. Любой активный участник видит все посты круга. Вход новых участников — только по приглашению владельца.
- Авторизация и проверка прав обязательны на сервере, включая выдачу изображений. Не заменяй их скрытием кнопок во frontend.
- Не добавляй микросервисы, GraphQL, JWT, Redis, Kubernetes, стороннюю авторизацию, AI-функции и платные сервисы без конкретной необходимости или нового запроса владельца.
- Не храни секреты, пароли, приглашения и cookie в git или логах. Не добавляй стандартный пароль администратора.
- Не удаляй реальные пользовательские данные и Docker volumes ради прохождения тестов. Тесты используют отдельную базу и отдельное хранилище.
- Локальная реализация, тестирование и подготовка инструкции развёртывания входят в задание. Покупка инфраструктуры и публикация на внешнем сервере требуют отдельного запроса владельца.
- Не объявляй первый релиз готовым по одному наличию файлов: нужны работающий сценарий двух пользователей и проверки закрытого доступа.

## Проверки

Точные команды добавь в README после создания проекта. Как минимум: форматирование Go, `go vet`, Go-тесты, интеграционные тесты с PostgreSQL, TypeScript typecheck, frontend lint/build, ключевые браузерные сценарии. Не подменяй PostgreSQL SQLite в интеграционных тестах. Для изменений только документации достаточно проверки ссылок и согласованности текста.
